# Med Check-in 2.4 Configurable Scales Design Brief

**Status:** Approved design for implementation planning  
**Date:** 2026-08-10  
**Target:** Med Check-in 2.4  
**Baseline:** Med Check-in 2.3.0, SQLite schema v2, portable JSON format v2  
**Scope:** Personal-use Windows application, one local data store

## Purpose

Med Check-in 2.4 finishes the configurability work started in 2.3 by making the core 0-10 scales first-class user-configurable definitions instead of fixed schema fields.

The release is intentionally narrow. It changes scale identity/storage, check-in rendering and validation, analytics, CSV export, and portable-data compatibility only where those surfaces depend on the fixed eight-scale model. It does not turn Med Check-in into a generic form builder or analytics platform.

The design follows three constraints:

1. **YAGNI:** implement only requirements needed by configurable 0-10 scales and compatibility with existing data;
2. **native first:** use SQLite relational constraints, the existing local HTTP server, native browser range inputs, and current application patterns rather than new dependencies or frameworks;
3. **one representation:** after migration, scale values have one canonical storage model rather than permanent built-in/custom branches.

## Goals

2.4 must let the user:

- add a 0-10 scale;
- rename a scale without changing historical identity;
- reorder active scales;
- archive a scale from future entry while retaining its historical meaning;
- restore an archived scale;
- use custom and archived scales naturally in history and analytics;
- upgrade from any database schema version currently supported by 2.3 without losing scale values;
- export and Replace-import scale definitions and values losslessly through the portable JSON format.

At least one scale must remain active at all times.

## Explicit non-goals

2.4 does **not** include:

- configurable minimums, maximums, steps, units, or scale types;
- text fields, yes/no fields, questionnaires, or a generic arbitrary-form builder;
- polarity/direction metadata such as "higher is better";
- icons, colors, categories, descriptions, or per-scale presentation settings;
- destructive deletion of scale definitions;
- composite scores, normalization, statistical significance, causal analysis, or automated health insights;
- JSON Merge import;
- general CSV import;
- cloud sync, accounts, sharing, or conflict resolution;
- a generic schema/migration framework;
- a generic configurable-definition framework shared with tracked items;
- unrelated UI, updater, installer, treatment, reminder, or runtime refactoring.

## 1. Scale definition model

Introduce a dedicated domain module, `backend/scales.mjs`, responsible for built-in definitions and scale-specific validation.

Each scale definition contains only:

```text
id
label
active
sortOrder
```

The eight current scales are seeded with their existing public IDs:

```text
mood
anxiety
irritability
energy
focus
functioning
sleepQuality
appetite
```

Those IDs are immutable. Renaming changes only the label.

Custom scale IDs are opaque stable IDs generated by the application, following the existing tracked-item convention, for example `custom:<uuid>`. Labels are trimmed, must be non-empty, and are limited to 120 characters.

Labels do not need to be unique. Identity is the stable ID, not display text.

Scale definitions cannot be deleted. They can only be activated or archived. Archiving the final active definition is invalid.

`sortOrder` is presentation order for active scales. Archived scales do not need a meaningful relative order. Restoring an archived scale appends it after the current active scales.

Do not generalize `tracked-items.mjs` and `scales.mjs` into one abstraction. Their product semantics overlap, but their observation storage and validation rules differ enough that a generic layer would add indirection without a current requirement.

## 2. SQLite schema v3

Advance `PRAGMA user_version` from 2 to 3.

Add:

```sql
CREATE TABLE scale_definitions (
  id TEXT PRIMARY KEY,
  label TEXT NOT NULL,
  active INTEGER NOT NULL CHECK(active IN (0,1)),
  sort_order INTEGER NOT NULL
) STRICT;

CREATE TABLE checkin_scale_values (
  checkin_id INTEGER NOT NULL REFERENCES checkins(id) ON DELETE CASCADE,
  scale_id TEXT NOT NULL REFERENCES scale_definitions(id),
  value REAL NOT NULL CHECK(value >= 0 AND value <= 10),
  PRIMARY KEY(checkin_id, scale_id)
) STRICT;
```

The schema may add simple definition-label/order checks if they match application validation, but it should not add speculative indexes or metadata.

Rebuild `checkins` without these fixed columns:

```text
mood
anxiety
irritability
energy
focus
functioning
sleep_quality
appetite
```

All other check-in columns and contracts remain unchanged.

The child table is preferred over a JSON scale-values column because SQLite already provides the referential integrity, uniqueness, range constraints, and transactional behavior the feature needs. Do not reimplement those properties in application JSON validation.

The database therefore has one canonical scale-value representation after migration.

## 3. Migration behavior

`backend/migrations.mjs` must preserve every database upgrade path supported by 2.3:

```text
schema v2 -> v3
schema v1 -> v3
recognized legacy schema v0 -> v3
fresh database -> v3
```

Do not require users to install intermediate application releases.

For an existing database, migration must:

1. checkpoint WAL as the current migration path does;
2. create the existing pre-migration backup before destructive schema work;
3. run migration in one `BEGIN IMMEDIATE` transaction;
4. seed the eight built-in scale definitions;
5. rebuild/copy the check-in table as required by the source schema;
6. copy every non-null legacy scale value into `checkin_scale_values` under the matching stable built-in ID;
7. preserve check-in IDs, semantic Day/Evening/Extra identity, timestamps, sleep fields, tracked IDs, notes, red flags, treatment history, settings, and reminder state;
8. set `user_version = 3` only after the migration succeeds;
9. roll back on failure while retaining/reporting the pre-migration backup.

For schema v2, existing configurable tracked-item definitions must remain unchanged. For schema v1/v0, the same tracked-item seeding/legacy transformations that 2.3 currently applies must still occur as part of the direct upgrade to v3.

Do not build a general migration registry solely for this release. Focused version branches/helpers are sufficient.

## 4. Repository and domain contract

Check-ins expose scale data as one object keyed by stable scale ID:

```json
{
  "scales": {
    "mood": 6,
    "energy": 4,
    "custom:...": 7
  }
}
```

The eight named scale properties disappear from the post-v3 domain model.

Repository reads should reconstruct the `scales` object from `checkin_scale_values`. Repository creates/updates must write the base check-in row and scale-value rows atomically.

### New scheduled check-in

For an ordinary new Day/Evening check-in, submitted scale IDs must equal the complete currently active scale set, and every value must be in the inclusive 0-10 range.

### Existing scheduled check-in

An existing scheduled record owns its historical scale set. Editing it must preserve exactly that set:

- values may be changed;
- values may not be removed;
- currently archived definitions already present on the record remain visible and editable;
- scales activated or created after the record was saved are not injected retroactively.

This prevents ordinary historical editing from changing the structure of old scheduled data.

### Extra check-in

An Extra observation may contain any subset of currently active scales plus the existing non-scale meaningful fields. Existing Extra observations may retain, edit, or remove scale values they already contain, including archived scale IDs. They may add only currently active scales. An archived scale may not be newly added to another observation merely by knowing its ID.

The existing Extra "must contain meaningful content" rule remains; an Extra may therefore contain no scale values when another meaningful field is present, but the complete observation may not be empty. Dynamic scales participate in that check instead of the fixed eight properties.

### Draft preservation and mismatch blocking

Browser drafts are unsaved historical work and already have a preservation contract across upgrades. A draft stores the scale IDs that were present when it was created.

When restoring a draft:

- existing values are preserved;
- known archived definitions referenced by the draft remain shown;
- scales created/activated later are not retroactively injected;
- a draft scale ID that is no longer known after a destructive Replace import is preserved in local draft state and blocks save rather than disappearing silently;
- a captured scheduled draft whose scale set no longer matches the current active set is preserved locally but blocks save until it is discarded and recreated under the current active scales.

Restored scheduled drafts do not bypass ordinary scheduled-entry validation and do not submit a scale-set exception to the backend. No server-side draft storage or definition-version history is needed for this preservation-and-blocking behavior.

Do not introduce definition revisions, audit history, server-side drafts, or a reconciliation subsystem for this edge case.

## 5. Scale-definition repository operations

Follow the existing tracked-item management shape rather than creating action-specific endpoints.

Repository operations should provide the equivalents of:

```text
listScaleDefinitions()
createScaleDefinition({ label })
updateScaleDefinition(id, { label?, active? })
reorderScaleDefinitions(orderedActiveIds)
```

Rules:

- creation produces an opaque stable ID and appends to active order;
- patch fields are restricted to `label` and `active`;
- archiving the last active scale fails;
- restore appends the definition to active order;
- reorder accepts the complete active-ID list, rejects duplicates/unknown/missing active IDs, and writes dense order values transactionally;
- inactive definitions are not part of the reorder payload.

Do not add delete operations.

## 6. Local HTTP API

Add scale definitions to `/api/v1/bootstrap` so the browser can render forms, history, settings, and analytics labels from one source.

Follow the existing tracked-item routes:

```text
POST /api/v1/scale-definitions
PUT  /api/v1/scale-definitions/:id
PUT  /api/v1/scale-definitions/order
```

There are no separate archive/restore endpoints. Archive and restore are ordinary updates to `active`.

The backend remains authoritative for:

- known IDs;
- 0-10 numeric values;
- required scheduled scale sets;
- historical scheduled scale-set preservation;
- archived-scale rules;
- at least one active scale;
- complete active reorder payloads.

Invalid scale input returns the existing ordinary HTTP 400 error style. Missing definitions use the existing 404 pattern where applicable. Do not add a new error/notification framework.

## 7. Browser UI

### Check-in form

Replace the eight static scale rows in `resources/index.html` with one empty scale container.

`resources/app.js` renders the same existing native range input primitive for the applicable scale definitions:

```html
<input type="range" min="0" max="10" step="1">
```

Do not replace the form with a frontend component framework or a custom slider implementation.

The rendered scale set depends on context:

- ordinary new scheduled form -> current active definitions;
- existing record -> that record's stored scale IDs, using current labels and showing archived status when applicable;
- restored draft -> the draft's stored scale IDs when they match the current active set; otherwise preserve the draft locally and show a blocked-save state;
- Extra -> current active definitions plus historically present archived definitions when editing an existing record.

The existing "use previous values" behavior should copy values only where the target form contains the same scale ID. It must not fabricate values for newly created scales.

### Settings

Extend the existing settings/configuration surface with a **Scales** section. It supports:

- add;
- inline rename;
- archive/restore;
- up/down ordering for active scales;
- a separate archived list.

Use simple up/down controls, matching the current tracked-item UI approach. Do not add drag-and-drop code or a dependency.

The UI disables archiving when only one active scale remains, while backend validation independently enforces the same invariant.

No colors, icons, descriptions, direction controls, units, or advanced scale settings are exposed.

## 8. Analytics

`backend/analytics.mjs` must stop importing/iterating a fixed `SCALE_FIELDS` list.

Analytics operate on dynamic scale IDs present in scheduled observations. Missing values mean no observation for that scale, never zero.

Return map-shaped scale data, for example:

```json
{
  "overall": {
    "mood": 6.4,
    "custom:...": 4.2
  },
  "daily": [
    {
      "date": "2026-08-10",
      "scales": { "mood": 6.5 },
      "rolling": { "mood": 6.2 }
    }
  ],
  "pairedDelta": {
    "mood": 1.1
  }
}
```

Existing calculations keep their current meaning:

- per-scale averages;
- daily aggregation;
- trailing smoothing;
- Day-vs-Evening paired deltas.

A paired delta for a scale uses only dates where both Day and Evening scheduled observations contain that same scale.

Archived scales remain analytically available when they have historical scheduled data. A definition with no observations in the selected period does not need a trend series.

Trend selectors and paired-comparison rows are generated from definitions that have usable data, rather than a hardcoded scale list.

Remove scale-specific KPI assumptions such as "average mood" and "average anxiety". Keep only configuration-independent summary KPIs such as scheduled observation count, represented days, and paired Day/Evening days.

Completion remains schedule-based. It is not recalculated from how many scale values exist.

Do not add normalization, polarity, composite scores, statistical testing, causal inference, or treatment-effect analysis.

## 9. Chart presentation

`resources/vendor/chart-lite.js` should accept dynamic scale IDs/definitions rather than own the eight medical labels.

Use a small fixed presentation palette and assign colors at render time. Color is not persisted and is not part of scale definitions, portable JSON, or API contracts.

Stable cross-reorder color identity is not a requirement.

## 10. Portable JSON format v3

Keep the existing format identifier:

```text
format = "med-checkin-2"
```

Advance only:

```text
formatVersion = 3
```

A v3 payload contains scale definitions separately from observations:

```json
{
  "format": "med-checkin-2",
  "formatVersion": 3,
  "scaleDefinitions": [
    {
      "id": "mood",
      "label": "Настроение",
      "active": true,
      "sortOrder": 0
    }
  ],
  "trackedItems": [],
  "observations": [
    {
      "id": 42,
      "scales": {
        "mood": 6
      }
    }
  ]
}
```

A valid v3 definition set must:

- contain every original built-in scale ID exactly once;
- contain unique IDs;
- contain valid labels/active/order values;
- contain at least one active scale;
- allow additional valid custom IDs.

Observation scale IDs must resolve against the payload's definitions and values must remain within 0-10. Historical observations may legitimately contain definitions currently marked inactive.

### v1/v2 compatibility

Portable v1 and v2 remain accepted.

Normalize legacy payloads at the import boundary into the v3-shaped model:

```text
legacy fixed named scale fields
-> seeded eight built-in scale definitions
-> observation.scales objects keyed by built-in IDs
```

The rest of repository/import code should operate only on the normalized v3 model. Do not scatter version-specific branches through persistence and analytics.

### Replace semantics

Portable import remains explicit **Replace** only.

Validation order:

1. format/version;
2. scale definitions;
3. tracked-item definitions;
4. observations against both definition sets;
5. treatment/settings and remaining payload contracts;
6. only then destructive replacement.

Replace keeps the existing pre-import backup and one-transaction replacement guarantees. Scale definitions and scale values are replaced in that same transaction with the rest of portable state. Local-only reminder transient state remains outside portable replacement as in 2.3.

Do not add Merge import or conflict-resolution behavior.

## 11. CSV export

Keep CSV as a wide convenience export with one row per observation.

Fixed observation metadata columns remain fixed. Dynamic scale columns follow, using the current display label for each scale definition represented in the exported data.

CSV is not the lossless interchange format. Portable JSON carries stable IDs and definition metadata. Do not add a companion CSV schema or generic import format solely to disambiguate intentionally duplicated labels.

## 12. Failure behavior

Keep failures ordinary and explicit:

- invalid/unknown scale definition or value -> HTTP 400;
- missing definition target -> 404 where the existing API uses that pattern;
- incomplete ordinary scheduled scale set -> 400;
- attempt to alter an existing scheduled record's scale set -> 400;
- attempt to newly use an archived scale -> 400;
- attempt to archive the final active scale -> 400;
- malformed reorder -> 400;
- restored draft containing an ID removed by Replace -> visible blocked-save state;
- migration/import failure -> transaction rollback plus the existing recoverable backup path.

Do not add reconciliation wizards, automatic data healing, conflict modals, or a generic notification system.

## 14. Acceptance criteria

2.4 is behaviorally complete when all of the following are true:

1. A fresh database seeds the eight current scales as active definitions and stores check-in scale values only in `checkin_scale_values`.
2. Existing schema v0/v1/v2 databases upgrade directly to v3 with a pre-migration backup and preserve every legacy scale value exactly under the matching built-in ID.
3. The user can add, rename, reorder, archive, and restore scales; no operation can leave zero active scales.
4. Renaming never rewrites historical observation identity.
5. New ordinary scheduled check-ins require the applicable full active scale set.
6. Existing scheduled check-ins retain exactly their historical scale set; values can change but cannot be removed.
7. Extra observations keep their looser non-empty semantics while respecting active/archive rules.
8. Restored browser drafts preserve their original known scale set and values across scale-definition changes; unknown IDs after destructive Replace block save rather than disappearing.
9. History renders current labels for stable IDs and can display archived scales on old records.
10. Analytics and chart controls work with custom, archived, and sparse scale histories without treating missing values as zero.
11. Completion semantics remain unchanged and schedule-based.
12. Portable JSON v3 round-trips definitions and scale values; v1/v2 imports normalize correctly; invalid Replace payloads cannot partially replace live data.
13. CSV export includes dynamic scale columns without becoming an import/interchange contract.
14. No cloud, generic form-builder, generic migration framework, or new dependency is introduced.
15. The full repository test gate and package verification pass after focused subsystem validation.

## 15. Validation expectations

The 2.3 source baseline has 126 passing Node tests under the repository's normal serial gate:

```text
npm test
```

Implementation should expand focused coverage for:

- scale definition seeding/create/update/reorder/final-active rejection;
- SQLite FK/range/uniqueness behavior;
- atomic check-in + scale-value writes;
- schema v0/v1/v2 -> v3 value preservation;
- scheduled create/edit scale-set invariants;
- Extra create/edit rules;
- archived historical editing;
- restored-draft preservation and unknown-ID blocking;
- v1/v2 portable normalization;
- v3 export/preview/Replace round-trip;
- failed Replace rollback;
- sparse/custom/archived analytics;
- paired deltas requiring both observations to contain the same scale;
- dynamic browser rendering and scale settings;
- dynamic chart series selection.

After each meaningful persistent-data or browser/API ownership boundary, run the relevant focused tests. Because the whole repository gate is cheap, run `npm test` before expensive exceptional-risk review so reviewers spend context on semantic/data-integrity risk rather than stale integration expectations.

Final repository validation is expected to include:

```text
npm test
npm run package:windows
```

No new destructive Windows upgrade behavior is introduced by this feature, so a release-level Windows smoke test should verify normal upgrade/data/draft preservation but does not require new installer-specific scenarios beyond the existing release process.

## 16. Execution Orchestration

Apply `AGENTS.md`, `.codex/ORCHESTRATION.md`, `.codex/PROJECT.md`, and `.codex/PLANNING_HANDOFF.md`.

### Repository map freshness

**Status:** fresh-enough.

**Evidence:** the 2.3.0 source snapshot was inspected on 2026-08-10, including `schema.mjs`, `migrations.mjs`, `domain.mjs`, `repository.mjs`, `data-maintenance.mjs`, `http-server.mjs`, `analytics.mjs`, browser files, focused tests, and the repository-specific orchestration adapter. GitHub `main` also reports package version 2.3.0.

**Explorer guidance:** skip a broad explorer pass unless implementation discovers meaningful drift from this map. Focused tracing inside an ownership boundary is fine when needed.

### Candidate ownership boundaries

1. **Persistence, migration, and portable-data integrity**
   - scope: scale domain model, schema v3, direct legacy migrations, repository read/write semantics, portable v3/v1/v2 normalization and Replace;
   - likely role: Terra workhorse candidate because this is predetermined but migration/data-integrity heavy;
   - exceptional-risk surface: schema rebuild, value preservation, Replace atomicity;
   - stop/escalate if current legacy schemas differ from the inspected migration assumptions or if a safe direct migration requires redesign.

2. **Browser/API/analytics product behavior**
   - scope: definition routes/bootstrap, dynamic forms/settings/drafts, analytics maps, trend selection/chart rendering;
   - likely role: Luna high candidate for the bounded pattern-following UI/API portion once persistence interfaces are stable, with primary/Terra handling any integration-heavy edge discovered;
   - stop/escalate if the browser draft lifecycle cannot preserve the approved snapshot semantics without a new persistent/server contract.

3. **Documentation/version/release integration**
   - scope: README/current contracts, project adapter, version metadata and package assertions after behavior is stable;
   - likely role: bounded implementation or primary integration; do not create a separate expensive review boundary solely for mechanical metadata.

These are candidate delegation units, not mandatory one-agent-per-section assignments.

### Review routing

- Run focused tests and the cheap full `npm test` gate before expensive semantic review of a completed boundary.
- **Terra review:** expected for coherent browser/API/analytics behavior and for one final whole-branch review because cross-boundary regressions are plausible.
- **Sol review:** conditional and narrow, only if the actual diff contains the expected exceptional-risk migration/Replace/data-integrity surface. Review migration preservation and destructive Replace semantics after normal tests are green.
- Do not multiply broad reviewers beyond concrete risk.

### Controlled workflow experiment

The measured 2.3 run identified a useful next experiment: use **Luna high rather than xhigh** on a comparable bounded UI/product implementation while keeping ownership boundaries and review policy otherwise stable. The browser/API/analytics boundary is a reasonable candidate if the primary judges it sufficiently bounded after persistence interfaces land.

Do not trade correctness for lower token use; compare reviewer findings and regressions alongside cost/churn metrics.

### Validation ownership

- child-focused checks: owning `test/*.test.mjs` files for each boundary;
- primary repository gate: `npm test` after meaningful integration and before exceptional-risk review;
- primary/package gate: `npm run package:windows` before completion;
- CI-owned evidence: Windows GitHub Actions sequence already defined by `.codex/PROJECT.md`;
- manual/environment check: normal previous-release -> 2.4 upgrade/data/draft smoke in a disposable Windows environment when release-level confidence is being established.
